# Mission Brief: Post-Onboarding Device-Testing Fixes

## Objective

Address issues discovered during real-device testing of the onboarding flow and home screen. This is a targeted fix mission, not a feature mission. Four concrete problems are in scope, plus related polish items surfaced by the testing.

## Execution Rules (Read First)

- Follow all rules in `KRAKEN_HUB_IMPLEMENTATION_PLAN.md` §0 Execution Rules and §2.1 Non-Negotiable Coding Rules.
- This mission fixes specific observed bugs. Do not add new features or "helpful improvements" outside the scope below.
- Each fix must include a regression test so the issue cannot silently return.
- Produce a Phase Completion Checklist at the end.
- Test each fix on both iOS simulator and Android emulator at multiple screen sizes before claiming complete.

## Phase 1: Restore the "Skip" Option on the Airplane Mode Demo Screen

### 1.1 Issue observed

On the onboarding demo screen (Screen 5 per `MISSION_BRIEF_ONBOARDING_FLOW.md` §1.5), the user has no way to skip the airplane mode exercise. The spec requires both "Try it" and "Skip and start using Kraken" as equally-weighted options, but the current build only offers the "Try it" path.

### 1.2 Required fix

Re-read `MISSION_BRIEF_ONBOARDING_FLOW.md` §1.5 in full. The current behavior does not match the spec.

The screen must display two buttons:

- **"Try it"** — disabled (grayed out) until airplane mode is detected, activates when it is.
- **"Skip and start using Kraken"** — always active, always visible.

Both buttons must have equal visual treatment. Neither should be styled as "primary" over the other. Neither should be smaller, lighter, or placed in a way that implies it's secondary.

Tapping "Skip and start using Kraken":
- Marks onboarding complete.
- Advances directly to the home screen.
- Does not show any confirmation dialog, "are you sure" prompt, or apology copy.
- The offline demo remains available afterward via settings → "See Kraken work offline" for users who want to try it later.

### 1.3 Regression test

Add an integration test that verifies:

- On fresh install, reaching `/onboarding/demo` shows both buttons.
- Both buttons are rendered at the same visual weight (same font size, same background treatment, same interactive area).
- Tapping Skip with airplane mode off advances to home and marks `isOnboarded = true`.
- Tapping Skip with airplane mode on also advances to home (airplane mode state does not affect the Skip path).
- After onboarding, the Skip path is no longer reachable; the demo is accessed via the settings entry point.

## Phase 2: Redesign the Recent Activity Feed on the Home Screen

### 2.1 Issues observed

The Recent Activity section on the home screen currently displays:

- Raw internal event identifiers like `shell_document_list` instead of human-readable descriptions.
- Routine framework events (shell loading a document list) that users don't care about.
- Multiple identical entries stacked up, creating a "river of noise" rather than useful information.

### 2.2 Root cause

The home screen is rendering the kernel's raw audit log without filtering for user-relevance or formatting for user readability. The audit log itself is correct — it captures everything as designed — but the home surface should display a filtered, formatted subset.

### 2.3 Required fix — classify audit events

Introduce an event classification in the audit log:

- **User-visible events:** things the user did (created a library, imported a document, recorded a meeting, generated a summary) or things the AI produced (a summary, a quote, a transcript). These are what the home screen should show.
- **System events:** routine framework operations (shell loaded a list, view rendered, BLoC state transition). These stay in the audit log for diagnostic purposes but never surface on the home screen.

Every event written to the audit log gets an `event_category` field with one of two values: `user_visible` or `system`. Existing events without a category default to `system` (conservative — don't surface anything until it's explicitly classified).

Audit this classification for every kernel and shell operation currently logging events. The following should be `user_visible`:

- Library created, renamed, deleted
- File added to library, file replaced, file removed
- Spoke access granted or revoked
- Recording started, stopped, transcribed, summarized (from Meeting Notes when it ships)
- Summary or draft generated by any spoke
- Export completed (any format)
- Passphrase changed
- Purge-all-data executed

The following should be `system` (never shown on home):

- Shell screen navigation events
- BLoC state transitions
- Framework resource loads
- Inference service state changes (unless they represent user-initiated inference)
- Vault read operations (too frequent to be meaningful)
- Search index upserts
- Any event whose description contains an internal identifier like `shell_document_list`

### 2.4 Required fix — home screen Recent Activity card

Replace the current home screen activity section with:

- A section heading: "Recent activity"
- Show at most **5 items**, filtered to `event_category = user_visible`.
- Each item displays:
  - A human-readable description (not an internal identifier).
  - A relative timestamp ("2 min ago," "1 h ago," "yesterday").
  - An icon indicating the type of event (optional but helpful).
- If there are more than 5 user-visible events, a subtle "View all activity" link opens the full Activity panel in settings.
- If there are zero user-visible events (e.g. a fresh install), show a quiet empty state: "Your recent activity will appear here."
- No duplicate consecutive entries. If a user imports 5 files into a library in quick succession, show one summarized entry ("Added 5 files to Pricing library") rather than 5 identical ones.

### 2.5 Required fix — human-readable event descriptions

Every `user_visible` event needs a plain-English description generated at write time, not an internal identifier.

Good examples:
- "Created library: Pricing"
- "Added 3 files to Contracts library"
- "Transcribed meeting: Q2 planning with Sarah"
- "Generated summary for: Acme pricing call"
- "Exported quote draft as PDF"

Bad examples (must not appear):
- `shell_document_list`
- `bloc_state_transition_123`
- `vault_read_op_4a7b`
- Any snake_case or camelCase internal identifier

If a description cannot be generated cleanly for some event type, classify it as `system` rather than showing a raw identifier to the user.

### 2.6 Regression test

- Generate a mix of 20 simulated events across user_visible and system categories; confirm the home screen shows only user_visible events, up to 5.
- Confirm no snake_case strings appear in any user-visible activity description.
- Confirm "View all activity" link appears when more than 5 user-visible events exist.
- Confirm duplicate consecutive events (e.g. 5 rapid file imports) are summarized, not listed individually.
- Confirm the full Activity panel in settings still shows everything, including system events in its detailed view, per the onboarding brief §3.

## Phase 3: Fix the "Bottom Overflowed by 6.7 Pixels" Rendering Bug

### 3.1 Issue observed

The Mock Spoke card in the Capabilities section shows a Flutter rendering overflow error ("BOTTOM OVERFLOWED BY 6.7 PIXELS") and the "Mock Spoke" label is truncated. This is a layout bug where the card's content exceeds its container height.

### 3.2 Required fix

Identify the widget producing the overflow. Likely candidates:

- A fixed-height container holding content that naturally needs more space.
- A `Column` with children whose combined intrinsic height exceeds the container.
- Text that doesn't wrap or truncate gracefully at the available width.

The fix is layout-level, not content-level:

- Use `Flexible` or `Expanded` where appropriate inside the card.
- Allow the card to size to its content, or constrain the content to fit the card height cleanly.
- Ensure the "Mock Spoke" label is fully visible at all supported font sizes (default, large, extra-large accessibility settings).

### 3.3 Regression test

- Render the home screen at each Android and iOS supported display density.
- Render at the default system font size and the largest accessibility font size.
- Confirm no overflow errors appear in the Flutter debug console at any size.
- Confirm the spoke name is fully visible on each card.

## Phase 4: Remove Internal Identifiers from User-Visible Surfaces

### 4.1 Issue observed

Strings like `shell_document_list` are appearing in user-facing contexts. These are internal event or widget identifiers that should never be visible to users.

### 4.2 Required fix

This is partially covered by Phase 2.5 above for activity descriptions. Extend the check to every user-visible surface:

- Audit all widget text strings across `/lib/shell/` and `/lib/spokes/`.
- Any string matching the pattern `[a-z]+(_[a-z]+)+` (snake_case) or `[a-z]+[A-Z][a-zA-Z]*` (camelCase) in user-visible text is a bug.
- Replace with human-readable descriptions.

### 4.3 CI guard

Add a lint rule or CI check that fails the build if user-visible strings contain snake_case or camelCase patterns. Allowlisted exceptions:

- Proper product names (none currently apply).
- File names in export contexts where users expect technical format (e.g. `meeting_2026_04_17.pdf` is fine because users recognize it as a filename).
- Diagnostic screens in the dev build (debug screen, developer tools — clearly labeled as dev-only).

### 4.4 Regression test

- Introduce a deliberate `test_snake_case` string in a user-visible widget in a test branch; confirm the CI check fails.
- Revert the deliberate string; confirm the CI check passes.

## Phase 5: Related Polish Issues

### 5.1 Library selector truncation

The library selector at the top of the home screen shows "Pricin..." or "Tech ..." instead of the full name. This is a truncation issue.

Required fix:
- Increase the selector's horizontal space allocation.
- If the name is too long for any reasonable space, truncate with clear middle-ellipsis ("Pricing L...brary") only as a last resort.
- Alternatively, move the selector to a dropdown that shows full names when opened.
- Limit library names to a practical maximum (80 characters is plenty) when users create them, with the input field enforcing this limit inline rather than allowing entry that will truncate later.

### 5.2 "Monitoring" word choice in the AI engine banner

The banner currently reads: "Gemma 4 is active and monitoring locally."

The word "monitoring" creates the wrong impression — it sounds like surveillance even though it's meant to mean "running and ready." Users scan copy quickly and "monitoring" triggers the wrong mental model for a privacy-first product.

Required fix — replace with one of these, whichever reads best in the UI:

- "Gemma 4 is running on this device."
- "Gemma 4 is ready on this device."
- "Gemma 4 is active on this device."

The subline "Your data never leaves your device" stays as-is.

### 5.3 Release-flavor verification

Confirm the Mock Spoke and any DEBUG-only surfaces are properly excluded from the release flavor per `KRAKEN_HUB_IMPLEMENTATION_PLAN.md` §6.1. The current screenshots show a DEBUG ribbon indicating a dev build, which is correct for testing — but verify the release flavor build excludes these before shipping.

Required verification:
- Build the release flavor locally.
- Confirm the Mock Spoke does not appear in the Capabilities section.
- Confirm the Mock Spoke nav tab does not appear.
- Confirm the DEBUG ribbon is not present.
- Confirm any debug screens are not reachable by any route.

## Phase 6: Tests and Verification

### 6.1 Unit tests

- Audit event classification logic: each known event type returns the expected category.
- Recent Activity card filters correctly to user_visible events only.
- Duplicate consecutive events are summarized into one entry.
- Human-readable description generation covers every user_visible event type.

### 6.2 Integration tests

- Fresh install → complete onboarding via Skip path → land on home → Recent Activity shows quiet empty state.
- Fresh install → complete onboarding via Try it path → land on home → confirm Recent Activity starts populated with relevant events only.
- Simulate 20 mixed events → home shows 5 most recent user-visible; Activity panel shows all 20.
- Library name entry: typing a 150-character name is limited to 80 characters with inline feedback.

### 6.3 Visual regression

Take before/after screenshots at multiple densities and font sizes. Attach to the PR. No rendering overflows, no truncated labels, no snake_case strings visible anywhere.

## Phase 7: Exit Criteria

All must pass on iOS simulator and Android emulator:

1. Onboarding demo screen shows both "Try it" and "Skip and start using Kraken" buttons with equal visual weight.
2. Skip path completes onboarding cleanly without confirmation dialogs or apology copy.
3. Home screen Recent Activity shows at most 5 user-visible events with human-readable descriptions.
4. No snake_case or camelCase identifiers appear in any user-visible string.
5. CI guard rejects user-visible strings with internal identifier patterns.
6. Mock Spoke card renders without overflow errors at all supported sizes.
7. All library names display fully or truncate gracefully with clear ellipsis.
8. AI engine banner no longer uses the word "monitoring."
9. Release flavor build confirmed to exclude Mock Spoke and debug surfaces.
10. All regression tests pass.
11. Phase Completion Checklist produced and committed.
